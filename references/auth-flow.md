## OAuth auth flow

`agy` uses OAuth via Antigravity (Google's authorization surface). There is no API-key path.

## Where the token lives

- `~/.gemini/antigravity-cli/antigravity-oauth-token` — file mode 0600. Not in the system keyring (the docs previously said it was; that's wrong for the CLI binary — it stores the token as a file in the antigravity-cli state directory).
- The token is regenerated by Antigravity and re-fetched by the CLI on each invocation; the CLI does not require the user to copy it around.

## First-run flow

On the first `agy` invocation (or after `/logout`), the CLI:

1. Spins up the language server.
2. Triggers a browser OAuth flow against the Antigravity auth page.
3. Locally, opens the default browser to the auth URL.
4. On remote/SSH/headless boxes, prints the URL to the terminal — the user must copy it to a local browser.
5. On completion, writes the token to `~/.gemini/antigravity-cli/antigravity-oauth-token` and populates `~/.gemini/antigravity-cli/settings.json` with the user's choices (model, project, telemetry).

The URL has a short validity window. If the user does not complete it in time, re-run `agy` to regenerate.

## The agent does not perform OAuth

The agent must not try to log in on the user's behalf. The CLI requires browser interaction for OAuth. The agent's job is to:

1. Detect the unauthenticated state by running `agy models` — if it returns a token-source error (`error getting token source: You are not logged into Antigravity`), the user is not authed.
2. Instruct the user to run `agy` interactively once to complete browser auth.
3. Wait for the user to confirm.
4. Re-run `agy models` to verify.

## Verifying auth

```bash
agy models
```

- Succeeds (prints the model list) → authed.
- Returns `error getting token source: You are not logged into Antigravity` → not authed. Have the user run `agy` interactively.

## Sign out

There is **no CLI flag** for sign-out. The flow is:

1. Run `agy` (TUI).
2. Type `/logout`.
3. The token is cleared from `~/.gemini/antigravity-cli/antigravity-oauth-token`.

The agent should document this in pre-flight: "`/logout` clears the OAuth token (TUI only)."

## First-run settings

`~/.gemini/antigravity-cli/settings.json` is populated on first run with the user's choices. Schema (as of v1.0.6):

```json
{
  "enableTelemetry": false,
  "gcp": {
    "project": "<antigravity-project-id>",
    "location": "global"
  },
  "model": "Gemini 3.1 Pro (High)"
}
```

- `enableTelemetry` — set to `false` to opt out. Edit the file to change after first run.
- `gcp.project` — the Antigravity project id. Edit the file to change after first run. **There is no CLI flag to set the project.**
- `gcp.location` — typically `"global"`.
- `model` — the default model, with effort suffix in parentheses (e.g. `Gemini 3.1 Pro (High)`).

The agent reads this file in pre-flight to learn the user's choices and reports them back.

## Headless / no-browser environments

If the user is on a remote box with no browser and no X11 forward, the auth URL is the only path — the user must copy it to a local machine. The agent must not attempt to launch a browser on the remote host.

If the user cannot reach `accounts.google.com` from the remote, they must run `agy` on a local machine to complete auth, then run `agy` on the remote. The OAuth token and settings.json are not portable across machines by default — the user must complete auth on each host.

## Re-auth

If `agy models` returns a token error mid-task, the token has been cleared or expired. The agent must:

1. Stop.
2. Ask the user to run `agy` interactively to complete browser auth.
3. Wait for confirmation.
4. Resume the conversation with `agy -c` (or `agy --conversation <id>` for a specific one).

The agent does **not** send a "re-auth prompt" to `agy` — there is no such prompt. The re-auth is a separate user action outside the conversation.
